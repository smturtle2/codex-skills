# 데스크톱 소통 UI 조사와 설계

조사일: 2026-09-06. 현재 요구 사항은 GUI가 있는 Linux·macOS·Windows에서 앱 밖으로 질문을 전달하는 스킬이다. CLI 전용·headless 환경은 제외한다. 여러 관련 요청을 한 창에 모으고, 에이전트가 상황에 맞춰 UI를 구성할 수 있어야 한다.

## 조사에서 확인한 내용

- KDE는 앱이 배경에 있을 때 조치 가능한 사건을 시스템 알림으로 전달하도록 안내한다. 일반 중요도에서도 지속 알림을 사용할 수 있다. 불필요한 알림과 색상 남용은 피한다. [KDE 상태 전달 지침](https://develop.kde.org/hig/status_changes/)
- GNOME은 알림이 보이지 않을 수 있으므로 내용을 앱에서도 확인할 수 있어야 한다고 설명한다. 오래된 알림 제거와 빈도 조절도 권고한다. [GNOME 알림 지침](https://developer.gnome.org/hig/patterns/feedback/notifications.html)
- GNOME의 액션 대화상자는 실행 전 옵션과 정보를 제시한다. 구체적인 동사로 버튼을 표시하고, 필요한 선택 전에는 제출을 비활성화한다. 일반 앱의 부모 창에 종속되는 모달 지침은 이번 독립 소통창에 그대로 적용되는 규칙은 아니다. [GNOME 대화상자 지침](https://developer.gnome.org/hig/patterns/feedback/dialogs.html)
- Microsoft는 알리기만 하는 경우와 알림 안에서 작업을 완료하는 경우를 구별하고, 목적에 맞는 버튼·입력·이미지를 선택하도록 한다. [Microsoft 알림 UX](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-ux-guidance)

이 자료를 이번 요구에 적용한 설계 제안은 **작은 주의 알림 + 관련 요청을 모은 하나의 커스텀 응답창**이다. 이것은 사용자 요구와 지침을 바탕으로 한 제품 설계 판단이며, 모든 OS가 강제하는 표준은 아니다.

## 필요한 기본 형태

| 출발 형태 | 적합한 상황 | 한 창 안의 구성 |
| --- | --- | --- |
| 간단한 요청 카드 | 짧은 선택이나 빠진 정보 | 짧은 맥락, 선택 버튼, 필요한 경우 직접 입력 |
| 복합 요청 폼 | 여러 관련 답변이 함께 필요 | 번호/제목으로 구분한 섹션, 필수·선택 표시, 통합 제출 |
| 비교·검토 화면 | 이미지나 제안을 보고 결정 | 나란히 놓은 후보, 차이와 근거, 의견 입력 |
| 자료 요청 화면 | 파일·이미지·긴 설명이 필요 | 첨부 영역, 미리보기, 설명 입력, 교체·제거 |
| 결과·막힘 알림 | 긴 작업 완료나 사용자 조치 필요 | 결과 또는 원인 요약, 다음 행동; 필요하면 같은 창에서 확장 |

복합 요청 폼을 중심으로 구현한다. 독립적인 작업을 무조건 묶지는 않는다. 같은 작업에서 함께 답할 수 있는 질문은 한 창에 모으고, 긴 내용은 스크롤·접기·단계 구성을 사용한다. 여러 창 생성은 실제 동작의 기본값이 아니며, 현재 동시에 띄운 창들은 디자인 비교용이다.

## 커스텀 범위

에이전트가 질문에 맞춰 창 크기, 열 배치, 섹션 순서, 카드/표/이미지, 입력 방식과 시각 강조를 바꿀 수 있도록 한다. 템플릿 선택만 가능한 고정 양식으로 제한하지 않는다. 예를 들어 이미지 두 개와 이유 입력, 제안 미리보기와 수정 입력, 여러 질문과 파일 첨부를 한 화면에 조합할 수 있다.

공통 계약은 UI와 분리한다.

1. 요청: request_id, task/session ID, 질문 맥락, 필요한 답변 필드.
2. 표현: 기본 템플릿 또는 커스텀 레이아웃과 에셋.
3. 제출: 안정적인 필드/action ID, 필수 항목 검증, 하나의 관련 답변 묶음, 원래 작업으로 전달.
4. 상태: 대기·제출·나중에·닫기·취소·전달 실패. 닫기와 답변은 별개이며, 입력값과 대기 요청을 보존한다.

접근성, 키보드 이동, 보이는 포커스, 충분한 대비와 긴 내용 처리는 커스텀 화면에도 유지한다. 임의 HTML/코드 렌더러를 채택한다면 표현 코드와 호스트 명령 실행 권한을 분리해야 한다. 커스텀 표현이 응답 전달 규칙까지 제각각 바꾸는 것은 아니다.

## 여러 데스크톱 환경 지원

OS 이름으로 스킬을 나누지 않고 요청 계약·렌더러·OS 알림 어댑터를 분리한다. Qt는 Linux·macOS·Windows용 공통 렌더러 후보지만 지원 버전과 아키텍처 조건이 있다. 현재 Qt 시안이 세 OS에서 검증됐다는 뜻은 아니다. [Qt 지원 플랫폼](https://doc.qt.io/qtforpython-6/overviews/qtdoc-supported-platforms.html)

HTML 기반 렌더링도 커스텀 구성의 후보지만, 일반 브라우저의 새 팝업은 사용자 동작이 필요할 수 있고 웹 알림에는 권한과 보안 컨텍스트 조건이 있다. 따라서 브라우저 탭 열기를 모든 데스크톱의 팝업 전달 구현으로 취급하면 안 된다. [MDN window.open](https://developer.mozilla.org/en-US/docs/Web/API/Window/open) · [MDN 웹 알림](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API)

Linux 시스템 알림도 actions·persistence 등 기능 지원이 서버마다 다르다. 공통 커스텀 응답창을 유지하고 알림은 어댑터로 취급하는 이유다. [freedesktop 알림 규격](https://specifications.freedesktop.org/notification/latest/protocol.html)

## 이번 산출물과 남은 구현 경계

스킬 정의, 복합 요청 폼의 네 가지 시각 시안, 네 가지 초기 구조 탐색을 제공한다. 현재 실행 확인 대상은 Linux GUI다. macOS·Windows 실행, 실제 알림 어댑터, 일반 커스텀 레이아웃 엔진, 영속 요청 저장, 에이전트 재개 연결은 아직 구현·검증하지 않았다.

KDE 전용 도우미는 최종 방향에서 제거했다. 다음 제품 구현은 하나의 창에 질문을 조합하는 렌더러와 공통 제출 계약을 중심으로 진행한다. 지금의 팔레트와 레이아웃은 디자인 시안이며 고정 명세가 아니다.
